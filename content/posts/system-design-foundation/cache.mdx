## Cache

Every time a page loads, the web server makes one or more calls to the database to fetch the data that page needs. When the same data is requested over and over, those repeated database calls become the thing that slows the application down. A cache is what you put in front of that work.

A cache is a small, fast, in-memory store that holds the result of an expensive operation or a piece of frequently read data. The first request pays the full cost, computing the result or querying the database, and the result is kept in the cache. Every request after that reads it straight from memory and skips the expensive work.

### The cache tier

The cache tier is a temporary data store layer that sits between the web tier and the data tier, and it is much faster than the database because it answers from memory. Giving it its own tier, rather than caching inside each web server's process, buys three things:

- **Better performance.** Reads that hit the cache are served from memory instead of going to disk-backed database queries.
- **Less database load.** Every cache hit is a database query that never happens, so the database has spare capacity for the writes and the uncached reads that actually need it.
- **Independent scaling.** The cache is its own pool of servers, so you can add cache capacity to match your read pattern without touching the database, and vice versa.

### Read-through cache

When the web server needs some data, it goes through the cache first:

1. Check the cache for the data.
2. If it is there (a cache hit), return it to the client.
3. If it is not (a cache miss), query the database, write the result into the cache, then return it to the client.

The cache fills itself lazily: a key only lands in the cache the first time something misses on it. This pattern, where the cache sits in the read path and loads from the database on a miss, is called a read-through cache.

Talking to a cache is simple, because most cache servers ship client libraries for the common languages. A typical Memcached call looks like this:

```
SECONDS = 1
cache.set('myKey', 'hi there', 3600 * SECONDS)
cache.get('myKey')
```

`set` stores a value under a key with a time to live, here one hour. `get` reads it back, or returns nothing if the key has expired or been evicted since.

### Other caching strategies

Read-through is one point in a larger space. Caching strategies split along two questions: how does data get into the cache, and how does the cache stay in step with the database when a write happens.

**Getting data in.**

- **Cache-aside (lazy loading).** The application code owns the logic: on a read it checks the cache, and on a miss it queries the database and writes the result back into the cache itself. The cache sits "aside" from the database and knows nothing about it. This is the most common setup, because it is simple and the cache only ever holds data that was actually asked for. The costs: the miss path is three steps spelled out in application code everywhere data is read, and a popular key expiring can fire a burst of identical queries at the database all at once, a cache stampede, covered in [its own post](/til/system-design-thundering-herd-problem).
- **Read-through.** Same read path, but the cache itself does the database load on a miss instead of the application. The application only ever talks to the cache. This keeps the miss logic in one place rather than scattered through the codebase, at the cost of a cache that has to be taught how to fetch from the source. The first read of any key still pays the full miss penalty.

**Keeping it in step on writes.**

- **Write-through.** Every write goes to the cache and the database together, as one synchronous operation. The cache is never stale, and a read right after a write always sees the new value. The price is paid on every write: it now carries both the cache and the database latency, and you end up caching data that may never be read.
- **Write-back (write-behind).** A write lands in the cache and returns immediately; the cache flushes to the database later, batched or after a short delay. Writes are fast, write-heavy bursts are absorbed, and repeated writes to the same key collapse into one database write. The risk is real: if the cache node dies before it flushes, those writes are gone, and until it flushes the database is behind the cache.
- **Write-around.** Writes go straight to the database and skip the cache; the key is only cached later, on a read miss. This suits data that is written but rarely read back soon after, since it avoids filling the cache with entries nobody reads. The tradeoff is that a read immediately after a write always misses.

Real systems combine one choice from each group. Cache-aside with write-around is a common pairing for read-heavy data that tolerates a little staleness; read-through with write-through is the choice when reads must always reflect the last write. The book stays with the read-through model, and that is enough to follow the rest of this chapter.

### When a cache is the right tool

Cache data that is read often and written rarely. A user's profile, a product description, the list of top posts on a page: read on nearly every request, changed once in a while. That is the ideal shape.

It is a poor fit for data you cannot afford to lose. A cache keeps everything in volatile memory, so if the cache server restarts, everything in it is gone. That is acceptable for a copy of something and unacceptable for the only copy. Anything that has to survive belongs in a persistent store, and the cache only ever holds a duplicate of it.

### Expiration policy

It is good practice to give cached entries an expiration time. When an entry expires it is dropped from the cache, so the next read for that key misses and reloads a fresh copy from the database.

The size of that window is a real tradeoff:

- **Too short**, and keys expire before they get reused, so the cache barely deflects any load and the database is queried almost as often as if there were no cache.
- **Too long**, and the cache keeps serving a value long after the database copy changed, so users see stale data.

Without any expiration policy, entries live in memory indefinitely, which both wastes space on data nobody reads anymore and maximizes how stale a served value can get.

### Consistency

The cache and the database hold two copies of the same data, and keeping them in agreement is its own problem. A write that changes the database and a write that updates or invalidates the cache are two separate operations, not one transaction, so there is always a moment where one has happened and the other has not. A crash or a race in that gap leaves the cache holding a value the database no longer has.

This gets harder as the system spreads across regions, because now there are multiple cache deployments to keep in sync with the database and with each other. Facebook's paper "Scaling Memcache at Facebook" is the standard reference for how far this problem goes at scale.

### When the cache fills up: eviction

A cache has a fixed amount of memory. Once it is full, storing a new entry means removing an existing one to make room. That removal is called cache eviction, and the rule for choosing the victim is the eviction policy:

- **Least Recently Used (LRU)** evicts whatever has gone longest without being read. This is the most common choice, because "not touched in a while" is usually a good proxy for "not needed soon".
- **Least Frequently Used (LFU)** evicts whatever has been read the fewest times, keeping popular keys even if they have gone briefly quiet.
- **First In First Out (FIFO)** evicts the oldest entry regardless of how often it is read.

LRU is the default; the others are worth reaching for when your access pattern has a shape LRU handles badly.

### When the cache goes offline

A single cache server is a single point of failure: a part of the system that, if it fails, takes the whole system down with it. It is the same problem we hit with one web server and one database. If the cache dies, every read misses and falls through to the database at once, and a database sized for cache-assisted traffic can fall over under the full unfiltered load.

Two mitigations, used together:

- **Spread the cache across several servers, in more than one data center**, so losing one server or one site takes out a fraction of the cache rather than all of it.
- **Overprovision memory** by some percentage above what you currently need, so a traffic spike or the loss of one node does not immediately push the remaining cache into constant eviction.

## The design so far

The web tier and the data tier are both redundant now, and a cache tier sits between them absorbing the repeated reads:

1. The client's request reaches a web server through the load balancer.
2. The web server checks the cache for the data it needs.
3. On a hit, it responds from the cache. On a miss, it reads from a slave database, writes the result into the cache, and then responds.
4. Writes still go straight to the master database.

Response times for dynamic data are in good shape. What is left is static content, the JavaScript, CSS, image, and video files that every page pulls and that do not need to come from your servers at all. Pushing those onto a content delivery network (CDN) is the next post.
