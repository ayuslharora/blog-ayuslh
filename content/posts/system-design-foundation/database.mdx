## Database

With the growth of the user base, one server is not enough, and we need multiple servers: one for web/mobile traffic, the other for the database. Separating web/mobile traffic (web tier) and database (data tier) servers allows them to be scaled independently.

### Which databases to use?

You can choose between a traditional relational database and a non-relational database. Let us examine their differences.

Relational databases are also called a relational database management system (RDBMS) or SQL database. The most popular ones are MySQL, Oracle database, PostgreSQL, etc.

Relational databases represent and store data in tables and rows. You can perform join operations using SQL across different database tables.

Non-Relational databases are also called NoSQL databases. Popular ones are CouchDB, Neo4j, Cassandra, HBase, Amazon DynamoDB, etc. Join operations are generally not supported in non-relational databases.

These databases are grouped into four categories:

- **Key-value stores:** data is a dictionary of keys mapped to opaque values, fetched by key. Examples: Redis, Amazon DynamoDB, Memcached.
- **Document stores:** values are semi-structured documents (JSON, BSON, XML) that you can also query by their fields. Examples: MongoDB, CouchDB, Amazon DynamoDB.
- **Column stores (wide-column):** think of one giant table where every row is found by a row key, but unlike SQL each row decides its own columns. Row 1 might have `name` and `email`, row 2 might have 900 columns none of which row 1 has, and you never declared them upfront. Related columns are grouped into "column families" and stored together on disk, so reading just a few columns across billions of rows stays fast and empty cells cost nothing. This layout is built for very high write volume and queries you can plan in advance. Examples: Cassandra, HBase, Google Bigtable.
- **Graph stores:** data is nodes and edges, and queries traverse the relationships directly. Examples: Neo4j, Amazon Neptune, JanusGraph.

A quick sense of where each of the databases named above fits:

- **CouchDB** (document store): stores self-contained JSON documents and syncs well across unreliable networks. Good for offline-first mobile or edge apps where each device holds a replica and reconciles changes later. In production: NPM's registry mirrors ran on CouchDB, and the Apple-backed PouchDB/Couch pairing powers apps that must keep working with no connection, because CouchDB's replication protocol was designed to merge divergent copies once a device comes back online.
- **Neo4j** (graph store): treats relationships as first-class. Reach for it when the connections between records are the query, social graphs, fraud rings, recommendation paths, network topology, where SQL joins would explode. In production: eBay uses it to compute shipping routes and NASA keeps a "lessons learned" knowledge graph in it, both cases where you ask "what is connected to what, how many hops away" and a graph traversal answers in milliseconds while the equivalent SQL is dozens of self-joins.
- **Cassandra** (wide-column store): built for massive write throughput and multi-datacenter replication with no single point of failure. Fits time-series, event logging, IoT feeds, and messaging where you write far more than you read and can design around known query patterns. In production: Discord stores trillions of chat messages in it and Netflix uses it for viewing history, both are append-heavy streams partitioned by a known key (channel id, user id) so writes spread evenly across the cluster and any node can go down without an outage.
- **HBase** (wide-column store on Hadoop/HDFS): sparse tables with billions of rows, tightly integrated with the Hadoop ecosystem. Suited to batch analytics and scan-heavy workloads over huge datasets already living in HDFS. In production: it long backed Facebook Messenger and still holds Yahoo and Pinterest analytics data, because the data already sits in Hadoop and the workload is large sequential scans feeding MapReduce/Spark jobs, not low-latency single-row lookups.
- **Amazon DynamoDB** (key-value / document store): fully managed, single-digit millisecond reads at any scale with no servers to run. A strong default for high-traffic web and mobile backends on AWS, shopping carts, user sessions, gaming state, where predictable latency matters more than flexible querying. In production: Amazon.com's own shopping cart and Lyft's ride-location store run on it, because traffic spikes 10x during peak events and DynamoDB absorbs that by auto-partitioning on the key without the team provisioning or tuning anything.

For most developers, relational databases are the best option because they have been around for over 40 years and historically, they have worked well. However, if relational databases are not suitable for your specific use cases, it is critical to explore beyond relational databases. Non-relational databases might be the right choice if:

- Your application requires super-low latency.
- Your data are unstructured, or you do not have any relational data.
- You only need to serialize and deserialize data (JSON, XML, YAML, etc.).
- You need to store a massive amount of data.
