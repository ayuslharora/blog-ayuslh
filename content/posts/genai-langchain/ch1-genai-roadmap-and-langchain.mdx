Generative AI moves so fast that new models, papers, tools, and jargon show up every week. Before writing any LangChain code, this post builds a map: by the end you should be able to take any GenAI term (RAG, RLHF, quantization, agents) and say where it belongs, and see exactly where LangChain fits.

## 1. What Makes Generative AI Different

Classical machine learning feeds a statistical algorithm lots of data so it can learn patterns and make predictions. It handles three kinds of problems:

| Problem type | What it outputs | Example |
|---|---|---|
| Regression | A number | Tomorrow's stock price of a company |
| Classification | A category from a fixed set | Is this photo a cat or a dog? |
| Ranking | An ordering | Products most similar to the one you're viewing |

None of these *create* anything. Classical ML picks from options or estimates a value; it was never used for problems that need human creativity.

**Generative AI** changed that. Its defining feature is that it creates new content: text, images, video, even code.

It sits at the innermost layer of the AI landscape:

- **AI** is the outer umbrella (symbolic AI, expert systems, fuzzy logic, and more).
- **Machine learning** is the most powerful technique inside AI.
- **Deep learning** is the part of ML that uses neural networks.
- **Generative AI** came out of deep learning once the **transformer architecture** arrived.

## 2. The Centre of Everything: Foundation Models

To organise a messy field you need one concept at the centre. In generative AI, that concept is the **foundation model**: an AI model trained at enormous scale, on close to "everything on the internet," using huge numbers of GPUs.

What makes it special isn't the size itself. It's what the size buys you: **foundation models are general, not specialised.**

A classical ML model built to predict a stock price does only that; it won't predict cricket scores. A foundation model can solve many different tasks with the same weights, because it has:

1. **A huge architecture** with a very large number of parameters, so it has the capacity to hold many skills.
2. **A huge amount of data**, so it has seen examples of nearly every kind of task.

### LLMs: the best-known foundation models

The most familiar foundation model is the **large language model (LLM)**, the backbone of generative AI today. One LLM can do text generation, sentiment analysis, summarization, and question answering.

Why can one model do all of that? An LLM is trained on a deceptively simple objective: predict the next word, across the text of the internet. But predicting the next word *well* across that much varied text forces the model to pick up much more. To continue a negative product review convincingly, it has to recognise that the review is negative. To continue "In summary," it has to know what a summary of the preceding text looks like. To continue a question with its answer, it has to know the answer. Those skills aren't trained in separately; they're learned as a side effect of getting next-word prediction right at scale.

Foundation models aren't limited to text: **large multimodal models (LMMs)** also work with images, video, and sound. For this series, you can mentally replace "foundation model" with "LLM."

## 3. Builder vs User: Sorting Every GenAI Term

With foundation models at the centre, the field splits cleanly in two. There are only two things you can do with a foundation model:

- **Build it.** The **builder perspective**: designing, training, and deploying foundation models, typically at a large company or research lab.
- **Use it.** The **user perspective**: taking an already-built foundation model and building applications on top of it.

Every GenAI term belongs to one of these sides (occasionally both). Whenever you hear a new one, ask: *"is this about building foundation models, or about using them?"*

| Term | What it is | Side |
|---|---|---|
| Prompt engineering | Phrasing and refining what you ask an LLM so it gives better answers | User |
| RLHF (reinforcement learning from human feedback) | Adjusting an LLM's behaviour and adding safeguards so it doesn't produce harmful or nonsensical output | Builder |
| RAG (retrieval-augmented generation) | Letting an existing LLM answer questions over your own private data | User |
| Pre-training | Training a foundation model from scratch on world-scale data with massive hardware | Builder |
| Quantization | Compressing a model so it can run in more environments | Builder |
| AI agents | Software built with an LLM that doesn't just answer but also *does* tasks for you (like booking a ticket) | User |
| Vector databases | Storage used when implementing RAG | User |
| Fine-tuning | Further training a model for a specific task | Both |

The rule of thumb: if the technique changes *how the model itself is made*, it's builder side. If it takes a finished model as given and works around it, it's user side.

The builder side covers the transformer architecture, types of transformers (like BERT and GPT), pre-training, optimization, fine-tuning, evaluation, and deployment of foundation models. It's the work of research labs, and it's not what this series is about.

## 4. The User Curriculum

The user side is about building applications on top of models that already exist. This is where LangChain lives, and it's what this series covers.

1. **Building basic LLM applications.** Models come in two kinds: closed source, used through their APIs, and open source, which you can run on your own machine with the Hugging Face library or on your machine or server with a tool like Ollama. This is also where you learn a framework like **LangChain** for building LLM-based applications.
2. **Improving the LLM's responses.** Three techniques, from lightest to heaviest:
   - **Prompt engineering:** the art and science of writing prompts (the input to a foundation model). Better prompts give better responses.
   - **RAG:** LLMs are trained on public data and know nothing about *your* data. RAG lets you show an LLM your private data and do question answering over it.
   - **Fine-tuning:** user-side fine-tuning is shallower than the builder-side kind, but it's still a real way to adapt a model to your task.
3. **AI agents.** Most LLM apps are chatbots that talk. An **agent** is a chatbot plus tools: it can take actions, not just reply. Ask a chatbot for the best tourist destinations in India and it answers "Goa." Give it access to booking tools and it can go on to book the trip for you.
4. **LLMOps.** Deploying LLM-based applications for real users, and continuously evaluating and improving them.
5. **Miscellaneous.** Multimodal models (audio or video as input or output) and diffusion models like Stable Diffusion.

## 5. Where LangChain Fits

The first step of the user curriculum is building basic LLM applications, and that's where this series starts.

**LangChain is an open-source framework for building LLM-based applications.** It provides modular components and end-to-end tools for building chatbots, question-answering systems, RAG-based applications, autonomous agents, and more.

Why it became so popular:

1. **It integrates with almost every LLM.** OpenAI's GPT models, Anthropic's Claude models, Google's Gemini models, and the open-source models on Hugging Face all connect through LangChain, so your application code doesn't have to be rewritten around each provider's SDK.
2. **It simplifies building LLM applications.** Concepts like **chains** let you link steps into pipelines, and pipelines are how you build complex applications without hand-wiring every step.
3. **It has integrations for everything around the LLM.** Real applications connect to databases, remote data sources, and cloud services like AWS. LangChain ships wrappers for these, so you skip the boilerplate.
4. **It's free and open source**, and very actively developed.
5. **It's an all-rounder.** Chatbots, agents, and RAG applications can all be built with it.

### Why start with LangChain?

Look back at the user curriculum: open- and closed-source models, APIs, Hugging Face, Ollama, prompt engineering, RAG, agents. LangChain touches *all* of them. Learning it first gives you hands-on experience across the whole user side, after which topics like prompt engineering and RAG can each be studied in depth.
