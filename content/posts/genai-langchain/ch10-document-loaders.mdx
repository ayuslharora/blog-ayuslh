Up to now this course covered the fundamentals: models, prompts, parsers, chains and runnables. This post starts something new: building **RAG applications** (retrieval-augmented generation). Before the details, one honest paragraph on why RAG exists.

## Why RAG Exists

A chat model only knows what it saw in training. It does not know today's news, it has never seen your emails, and it has never read your company's internal documentation. Ask it about any of those and it either says it does not know or, worse, makes something up.

The fix is to give the model an **external knowledge base** (a pile of PDFs, a database, your notes) and let it look things up before answering. Retrieval finds the relevant pieces of the knowledge base; the model then writes an answer using those pieces as context. That is RAG: information retrieval plus language generation. It also helps with privacy (your documents stay in your own system instead of being uploaded to a chat website) and with size (a book does not fit in one prompt, but you can split it into pieces and retrieve only the relevant ones).

A RAG application is built from four components, and the next four posts cover them one at a time:

1. **Document loaders** (this post): get data from any source into LangChain.
2. **Text splitters**: cut long documents into pieces.
3. **Vector stores**: store the pieces so they can be searched by meaning.
4. **Retrievers**: fetch the pieces relevant to a question.

After that we wire them together into a full application.

## What a Document Loader Does

Data lives in many places: PDFs, text files, databases, websites, cloud drives, Slack. Every one of those has its own format and its own way of being read. If each came into your program in its own shape, every later step (splitting, embedding, searching) would need special cases per source.

LangChain's answer is one standard shape, the **`Document`** object, and a **document loader** is any component that reads a source and returns documents. A `Document` has two main fields:

- `page_content`: the actual text.
- `metadata`: a dictionary about the text: where it came from, which page, which row, and so on.

Two rules hold for every loader, and learning them once covers all of them:

1. You create the loader with its source (a path or a URL), then call `.load()`.
2. `.load()` always returns a **list** of `Document` objects, even when there is only one.

### Where to Get Loaders in 2026

Older tutorials import ready-made loaders (`TextLoader`, `PyPDFLoader`, `CSVLoader`, `WebBaseLoader`, `DirectoryLoader`) from `langchain_community`. That package, and its JavaScript twin `@langchain/community`, were **sunset in 2026** and are no longer maintained; the official docs now say the PDF and text loaders "should no longer be used". The ready-made options today are standalone partner packages, each for a specific kind of source:

| Need | Where to look |
|---|---|
| PDFs with layout, tables, OCR | `langchain-docling`, `langchain-pymupdf4llm`, `langchain-unstructured` |
| Websites at scale (crawling, JavaScript pages) | `langchain-firecrawl`, `langchain-apify` |
| Cloud storage | the provider's own package, for example `langchain-google-community`, `langchain-azure-storage` |
| Plain text, CSV, a local folder | no package: write the few lines yourself |

The last row is not a downgrade, it is how loaders were always meant to work. A loader is just a small class that yields `Document`s, and LangChain's base class does the rest. So instead of memorising a catalogue, this post builds the five common loaders from scratch. Once you can do that, you can load anything.

**Setup.** Python examples ran on LangChain 1.4.9 (langchain-core 1.7.6) with `pypdf`, `requests` and `beautifulsoup4`. The JavaScript ones ran on @langchain/core 1.3.5 with `unpdf`, `cheerio` and `d3-dsv`. Everything LangChain-related comes from `langchain-core` / `@langchain/core`. The code blocks build on each other: later ones reuse the imports (`Path`, `Iterator`, `BaseLoader`, `Document`, `readFile`, ...) shown in the first.

## The Pattern: A Loader Is a Class That Yields Documents

In Python, subclass `BaseLoader` and implement `lazy_load`, a method that **yields** one `Document` at a time. The base class then gives you `.load()` for free: it just collects everything `lazy_load` yields into a list. In JavaScript, subclass `BaseDocumentLoader` and implement `load()`.

Here is the smallest useful loader: a text file becomes one `Document`.

<CodeTabs>

```python
from pathlib import Path
from collections.abc import Iterator

from langchain_core.document_loaders import BaseLoader
from langchain_core.documents import Document


class TextFileLoader(BaseLoader):
    """One Document for the whole file."""

    def __init__(self, path: str, encoding: str = "utf-8"):
        self.path, self.encoding = path, encoding

    def lazy_load(self) -> Iterator[Document]:
        text = Path(self.path).read_text(encoding=self.encoding)
        yield Document(page_content=text, metadata={"source": self.path})


docs = TextFileLoader("cricket.txt").load()

print(type(docs), len(docs))
print(docs[0].page_content[:40])
print(docs[0].metadata)
```

```js
import { readFile } from "node:fs/promises";
import { Document } from "@langchain/core/documents";
import { BaseDocumentLoader } from "@langchain/core/document_loaders/base";

class TextFileLoader extends BaseDocumentLoader {
  constructor(path) {
    super();
    this.path = path;
  }

  async load() {
    const text = await readFile(this.path, "utf-8");
    return [new Document({ pageContent: text, metadata: { source: this.path } })];
  }
}

const docs = await new TextFileLoader("cricket.txt").load();

console.log(Array.isArray(docs), docs.length);
console.log(docs[0].pageContent.slice(0, 40));
console.log(docs[0].metadata);
```

</CodeTabs>

```
<class 'list'> 1
Cricket is a bat-and-ball game.
Two team
{'source': 'cricket.txt'}
```

`cricket.txt` here is a two-line file. The `encoding="utf-8"` matters when a file contains special characters; without it a file with accented letters or emoji can fail to decode. The result is a list with one `Document`: the whole file as `page_content` and the path in `metadata`.

Because a loader returns normal objects, it plugs straight into chains. Pull the text out and feed it to the `prompt | model | parser` chain from earlier posts: `chain.invoke({"poem": docs[0].page_content})`. You can also wrap the loader's `.load` in a `RunnableLambda` so that loading becomes a step of the chain.

## A PDF Loader: One Document per Page

For PDFs the natural unit is a page: **one `Document` per page**, with the page number in the metadata. `pypdf` (Python) and `unpdf` (JavaScript) read the PDF's text layer.

<CodeTabs>

```python
from pypdf import PdfReader


class PdfPageLoader(BaseLoader):
    """One Document per PDF page."""

    def __init__(self, path: str):
        self.path = path

    def lazy_load(self) -> Iterator[Document]:
        reader = PdfReader(self.path)
        for i, page in enumerate(reader.pages):
            yield Document(
                page_content=page.extract_text(),
                metadata={"source": self.path, "page": i, "total_pages": len(reader.pages)},
            )


pages = PdfPageLoader("curriculum.pdf").load()

print(len(pages))
print(pages[0].page_content)
print(pages[0].metadata)
```

```js
import { extractText, getDocumentProxy } from "unpdf";

class PdfPageLoader extends BaseDocumentLoader {
  constructor(path) {
    super();
    this.path = path;
  }

  async load() {
    const pdf = await getDocumentProxy(new Uint8Array(await readFile(this.path)));
    const { text, totalPages } = await extractText(pdf, { mergePages: false });
    return text.map(
      (pageText, i) =>
        new Document({ pageContent: pageText, metadata: { source: this.path, page: i, total_pages: totalPages } })
    );
  }
}

const pages = await new PdfPageLoader("curriculum.pdf").load();

console.log(pages.length);
console.log(pages[0].pageContent);
console.log(pages[0].metadata);
```

</CodeTabs>

```
3
Deep learning curriculum, page 1
{'source': 'curriculum.pdf', 'page': 0, 'total_pages': 3}
```

This ran on a small 3-page sample PDF. A 23-page PDF would give 23 documents, a 300-page book 300. The page index starts at 0, so `'page': 0` is the first page.

This is the simple version, and its limits are the limits of reading a PDF's text layer. It will not read a scanned PDF (which is just pictures of pages), and it handles tables and complicated layouts poorly. Those are the cases the PDF packages in the table above exist for: Docling and PyMuPDF4LLM keep layout and tables, Unstructured can do OCR. They all return the same thing, a list of `Document`s, so swapping one in later changes only the loader line.

## A Folder Loader: Many Files at Once

What if a folder holds many files? Write a loader that takes a folder, a glob pattern for which files to pick (`*.pdf` is every PDF in the folder, `**/*.txt` is every text file in every subfolder) and the loader class to use on each match.

<CodeTabs>

```python
class FolderLoader(BaseLoader):
    """Run a loader on every file matching a glob, one file at a time."""

    def __init__(self, folder: str, glob: str, loader_cls):
        self.folder, self.glob, self.loader_cls = folder, glob, loader_cls

    def lazy_load(self) -> Iterator[Document]:
        for path in sorted(Path(self.folder).glob(self.glob)):
            yield from self.loader_cls(str(path)).lazy_load()


loader = FolderLoader("books", "*.pdf", PdfPageLoader)
print(len(loader.load()))
```

```js
import { readdir } from "node:fs/promises";

class FolderLoader extends BaseDocumentLoader {
  constructor(folder, extension, LoaderClass) {
    super();
    Object.assign(this, { folder, extension, LoaderClass });
  }

  async load() {
    const names = (await readdir(this.folder)).filter((n) => n.endsWith(this.extension)).sort();
    const docs = [];
    for (const name of names) {
      docs.push(...(await new this.LoaderClass(`${this.folder}/${name}`).load()));
    }
    return docs;
  }
}

const loader = new FolderLoader("books", ".pdf", PdfPageLoader);
console.log((await loader.load()).length);
```

</CodeTabs>

```
6
```

With two sample PDFs of 3 pages each, that prints `6`: one document per page, across all files. Pointed at three machine learning books of 326, 392 and 468 pages, the same code gives 1186 documents. Each document's `metadata["source"]` tells you which book it came from. Because the folder loader takes the per-file loader as an argument, it works with any loader, not only PDFs.

## load vs lazy_load

Loading three large books takes noticeable time, and that raises a real question: what happens with 100 books, or 500? Two problems appear:

- **Time.** Nothing is returned until every file has been read.
- **Memory.** `.load()` builds *every* `Document` and holds them all in a list at once. With enough files that no longer fits in RAM.

The fix is **lazy loading**. Every Python loader also has `.lazy_load()`; in fact it is the method you wrote. It returns a **generator**: it reads and hands you one `Document` at a time, only when you ask for the next one.

| | `.load()` | `.lazy_load()` |
|---|---|---|
| Returns | A list of all documents | A generator of documents |
| Memory | Everything at once | One document at a time |
| First result | After everything is loaded | Immediately |
| Use when | Few or small files, and you need them all together | Many or large files, or you can process each document and move on |

```python
for doc in loader.lazy_load():
    print(doc.metadata["source"], doc.metadata["page"])
```

```
books/dl-basics.pdf 0
books/dl-basics.pdf 1
books/dl-basics.pdf 2
books/ml-basics.pdf 0
...
```

With `.load()` and a big folder you stare at a blank terminal until all the work is done; with `.lazy_load()` the first line prints right away, and each document is processed and then released before the next arrives. The catch is that you handle documents as they stream past, so you cannot index into the result (`docs[5]`) or ask for its length without consuming it. Notice that `FolderLoader` is lazy end to end: it opens one file, yields its pages, and only then opens the next.

LangChain.js loaders have only `load()`, with no lazy variant. The JavaScript tab above is already the equivalent for big folders: it loads one file at a time, so you can process each file's documents inside the loop instead of collecting them all.

## A Web Page Loader

To load the text of a web page: fetch the HTML, then strip the tags so only readable text is left. Python uses `requests` plus Beautiful Soup; JavaScript uses `fetch` plus `cheerio`.

<CodeTabs>

```python
import requests
from bs4 import BeautifulSoup


class WebPageLoader(BaseLoader):
    """The visible text of a web page (works on static pages)."""

    def __init__(self, url: str):
        self.url = url

    def lazy_load(self) -> Iterator[Document]:
        html = requests.get(self.url, timeout=30, headers={"User-Agent": "my-app"}).text
        soup = BeautifulSoup(html, "html.parser")
        title = soup.title.string if soup.title else ""
        yield Document(page_content=soup.get_text(" ", strip=True), metadata={"source": self.url, "title": title})


docs = WebPageLoader("https://example.org").load()

print(len(docs))
print(docs[0].page_content[:60])
print(docs[0].metadata)
```

```js
import { load as parseHtml } from "cheerio";

class WebPageLoader extends BaseDocumentLoader {
  constructor(url) {
    super();
    this.url = url;
  }

  async load() {
    const html = await (await fetch(this.url, { headers: { "User-Agent": "my-app" } })).text();
    const $ = parseHtml(html);
    $("script, style").remove();
    const text = [$("title").text(), $("body").text()].join(" ").replace(/\s+/g, " ").trim();
    return [new Document({ pageContent: text, metadata: { source: this.url, title: $("title").text() } })];
  }
}

const docs = await new WebPageLoader("https://example.org").load();

console.log(docs.length);
console.log(docs[0].pageContent.slice(0, 60));
console.log(docs[0].metadata);
```

</CodeTabs>

```
1
Example Domain This domain is for use in documentation examp
{'source': 'https://example.org', 'title': 'Example Domain'}
```

To load several pages, make one `Document` per URL (loop over a list of URLs inside the loader). Plug the page text into a prompt with `{text}` and `{question}` variables and you can ask questions about any page; if the page does not contain the answer, a well-prompted model says so, which is the behaviour you want.

This works on static pages (blogs, news articles, documentation). It does not work on pages that build their content with JavaScript after loading, because we only see the first HTML the server sends. For those you need a browser-driven tool or a crawling service (the Firecrawl and Apify packages in the table). A nice project idea: a Chrome extension that, on any page you open, loads that page and lets you chat with it.

## A CSV Loader: One Document per Row

For a CSV file make **one `Document` per row**, with the text written as `column: value` lines and the row number in the metadata.

<CodeTabs>

```python
import csv


class CsvRowLoader(BaseLoader):
    """One Document per row, written as 'column: value' lines."""

    def __init__(self, path: str):
        self.path = path

    def lazy_load(self) -> Iterator[Document]:
        with open(self.path, newline="", encoding="utf-8") as f:
            for i, row in enumerate(csv.DictReader(f)):
                text = "\n".join(f"{k}: {v}" for k, v in row.items())
                yield Document(page_content=text, metadata={"source": self.path, "row": i})


rows = CsvRowLoader("ads.csv").load()

print(len(rows))
print(rows[0].page_content)
print(rows[0].metadata)
```

```js
import { csvParse } from "d3-dsv";

class CsvRowLoader extends BaseDocumentLoader {
  constructor(path) {
    super();
    this.path = path;
  }

  async load() {
    const rows = csvParse(await readFile(this.path, "utf-8"));
    return rows.map(
      (row, i) =>
        new Document({
          pageContent: Object.entries(row).map(([k, v]) => `${k}: ${v}`).join("\n"),
          metadata: { source: this.path, row: i },
        })
    );
  }
}

const rows = await new CsvRowLoader("ads.csv").load();

console.log(rows.length);
console.log(rows[0].pageContent);
console.log(rows[0].metadata);
```

## Why Writing Loaders Is the Normal Thing to Do

Every ready-made loader that ever existed was written this way: someone had a data source with no loader, wrote a `BaseLoader` subclass, and shared it. The community package that collected hundreds of them is retired, but the mechanism did not change. If your source is a database, a Notion export or an internal API, the recipe is the same three steps: read the data, turn each natural unit (page, row, record) into a `Document` with useful metadata, and `yield` it.

| **RAG** | Give the model an external knowledge base: retrieve relevant pieces, then generate an answer from them. Fixes stale knowledge, private data and documents too big for one prompt |

| **`Document`** | `page_content` (the text) plus `metadata` (source, page, row...). The one shape every loader returns |
| **The loader pattern** | Create the loader with its source, call `.load()`, get a *list* of `Document`s |
| **Community loaders are retired** | `langchain_community` / `@langchain/community` were sunset in 2026. Use standalone partner packages for specialised sources, or write the loader yourself |

| **Text / PDF / CSV / web** | One document for the file / one per page (`pypdf`, `unpdf`) / one per row (`csv`, `d3-dsv`) / the page text (`requests` + Beautiful Soup, `fetch` + `cheerio`) |
| **Folder loader** | Folder + glob + the loader to use per file; yield each file's documents in turn |
